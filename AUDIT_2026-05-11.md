# ollie · audit · 2026-05-11

## 1. Executive summary

- Shape's good. 14 packages, ~67k lines of TS, build is green, typecheck is green. 1067 of 1069 unit tests pass. The constitutional rules (Burhan never decays, banned phrases blocked, research-stream opt-in, no engagement pushes) are actually enforced in code.
- **The single biggest risk is auth.** The sign-up flow generates a random Supabase password and throws it away. Sign-in then sends the user's passphrase to Supabase as the password (`packages/auth/src/index.ts:230`). Supabase's heap/logs see the passphrase. Pair that with: same passphrase derives the AES key client-side → if Supabase ever leaks the auth attempt, every blob is decryptable. The "zero-knowledge" promise in the file header is not what's implemented.
- **The second biggest risk is silent failures of "shipped" work.** Sprint 2 (sync, auth, backup), Sprint 4 (research-stream) all have tests and code — but **none of them are imported anywhere in apps/web or apps/desktop**. They never boot. The user gets local-only storage no matter what the sprint summaries claim.
- **Sync has 2 broken tests today.** `pnpm -r test` fails in `@ollie/sync`. The summaries say "deflaked." It's not.
- Best win recently: the cross-module router (Sprint 3 D2) and Burhan additive-only tree (Sprint 3 D1) are genuinely well-structured. The router has a TTL, a debug lineage log, reflect rules — and no event loops. Burhan logic is air-tight (deterministic positioning, dedupe by id, no decay function exists anywhere).
- Notifications are real and shipped. The dispatcher has dedupe, budget, mute, aggregation, and the type system literally cannot express an engagement category. Web/Electron backends installed at boot. APNs worker is plausible but not deployed (Apple key blocker).
- iOS shell does not exist yet — `apps/ios/` is a Capacitor stub with no `pnpm cap add ios` run. The voice / push / intents are designed but only desktop has working hardware.
- 21 banned-phrase patterns pass cleanly across all source. The scanner is wired as a pretest. This is the kind of guard that scales — keep adding to it.
- Garden growth/water in `GardenScreen.tsx` is a hard-coded constant (`growth: 0.42, water: 0.72`). The mini-Burhan tile uses the real life-event tree. The garden full-screen view uses fake decoration.
- **The architecture rule "UI reads derived values from store; orchestrator calls logic" is half-violated.** Every module UI file imports `@ollie/logic/*` directly and runs detectors inside `useMemo`. Pragmatic, but it means logic runs twice (once in the UI, once in the orchestrator).

## 2. CRITICAL findings

### C1 · Sign-in sends the passphrase to Supabase as the password — `packages/auth/src/index.ts:230`

The doc comment at the top of the file (`packages/auth/src/index.ts:6-20`) describes "Pattern A" — the server stores a random password, never the passphrase, and the passphrase is only used client-side to derive the encryption key. What's actually implemented is "Pattern B" — `signIn` calls `deps.api.supabase.auth.signInWithPassword(input.email, input.passphrase)` directly. Supabase only bcrypt-hashes that password, but it sees the plaintext at TLS termination, in request bodies, and in audit logs.

The signup `serverPassword = generateRandomServerPassword()` is generated, sent once, and never persisted anywhere — so sign-in cannot recover it.

**Why it matters:** Your user data encryption key is derived from the same passphrase. If Supabase ever logs request bodies, has a breach, or an insider snoops the auth table heap, the attacker has the passphrase → they have the key → every encrypted blob in `encrypted_state` decrypts. The "zero-knowledge" claim in your marketing copy would be a lie.

**Fix:** Either commit to Pattern B in the docs and explain the threat model honestly ("Supabase is in our TCB"), OR ship Pattern A — store the random `serverPassword` encrypted inside the user's profile row (encrypted under the passphrase-derived key, with the salt). Sign-in flow: fetch profile by email, decrypt the random password, then sign in to Supabase with it. Mixed result of decryption → "wrong passphrase". This is correctly described in the file's inline note at line 209-225 but never implemented.

### C2 · `@ollie/auth`, `@ollie/sync`, `@ollie/backup`, `@ollie/research-stream` are never imported by any app

`grep -rn "@ollie/sync\|@ollie/auth\|@ollie/backup\|@ollie/research-stream" apps/` returns zero hits in `apps/web/src` and `apps/desktop`. These packages have full code, full tests, but no app instantiates them. Sprint summaries SPRINT_2_SUMMARY.md and SPRINT_4_SUMMARY.md claim these systems shipped.

**Why it matters:** Users get local-only storage on a single device. The whole multi-device sync promise (a paid-tier feature) is non-functional. Same for encrypted export/import. Same for B2B research opt-in. The infrastructure exists but isn't plugged in.

**Fix:** A new file `apps/web/src/lib/account-boot.ts` that:
1. Tries to read `shared.auth.session` from store.
2. If session exists and not expired → create `authClient` + recover encryption key (you'd need to prompt for passphrase if not cached in memory) → start `syncClient.start()` → optionally start `researchStream`.
3. If no session → leave everything off; UI shows "sign in to sync".

Import that boot file in `main.tsx`. ~1 day of work to wire what already exists.

### C3 · `pnpm -r test` fails today — `packages/sync/tests/sync.test.ts:120, 137`

Two sync outbound tests are red. Both are timer-related — they assert `captured.upserts.length === 1` after `vi.runAllTimersAsync()` and `queueDepth > 0` after `advanceTimersByTimeAsync(500)`. SPRINT_4_SUMMARY.md claims "sync test deflaked with explicit `runAllTimersAsync`." Not anymore.

**Why it matters:** The pretest scanner gates voice. The vitest suite gates everything else. If `pnpm test` is red, you can't trust any green-ticket claim in a future sprint summary, and your CI (if you add one) will be broken on day one.

**Fix:** Either fix the timing in the test, or run with `--retry 2` if it's truly flaky. Investigate root cause first — the `drainOnce` path checks `isOnlineFn()` and the test toggles online/offline, so check whether the test's online flag is being read at the right tick.

### C4 · Cron worker has no retry policy and resets `attempts` to 1 — `apps/api/src/worker.ts:224`

`updateJob` PATCHes `attempts: (patch.attempts as number | undefined) ?? 1`. The caller in `runCron` (lines 144-167) never passes `attempts`, so every patch hard-sets `attempts = 1`. The status flips to `'fired'` or `'failed'` on the first try with no exponential backoff. The schema has a partial unique index on `(user_id, dedupe_key)` only WHERE status='pending', so a permanently-failed job can never be retried even by client logic.

**Why it matters:** A transient APNs failure or Supabase timeout turns into a permanent miss. Critical for the medication-reminder use case — if APNs is flaky for 30 seconds, the user gets nothing, and the next dose's reminder may collide with the dedupe.

**Fix:** Change to `attempts: (job.attempts ?? 0) + 1`. Add a max-attempts check (e.g. ≤ 5) before marking `failed`. Add a `failed_at_attempt < max` retry path that keeps `status = 'pending'` and bumps `fire_at` by `2^attempts` minutes.

### C5 · Encrypted-state migration has no backup-before-migrate — `packages/store/src/migrations.ts:57-62`

If a migration callback throws, the code logs the error and **continues to write the meta as if migration succeeded** (line 63). The legacy void-app design described "snapshot every void-namespaced key to `void.state._backup.pre_migration.<ts>`" — the comment in this file admits it's "deferred to a later phase." It's still deferred.

**Why it matters:** A buggy migration on a real user's device silently corrupts their data, then sets `version = STORE_VERSION`, so no future migration ever runs. The user's data is locked in a half-migrated state with no way back.

**Fix:** Wrap `runMigrations` in a `try { snapshot every void.state.* key → void.state._backup.pre_migration.<ts> }` first. On migration failure, restore the snapshot and refuse to bump the meta version. Surface "your data was rolled back; this is a bug" to the user. Pre-launch this is fine; the moment you have one real user, it's load-bearing.

## 3. HIGH findings

### H1 · Web app doesn't request Notification permission until first `notify()` — `packages/notifications/src/backends/web.ts:31-37`

Permission is requested lazily on the first notify call. That call may come from a background scheduler tick when the user isn't looking at the page, and Chrome blocks permission prompts that aren't tied to a user gesture. Users will silently never get a permission prompt.

**Fix:** Add an explicit "turn on reminders" toggle in onboarding (and settings) that calls `Notification.requestPermission()` from a click handler. Until then, dispatcher should treat web as "no platform" and log only.

### H2 · Web push (PWA / Safari iOS) is not implemented — `apps/web/public/sw.js`

The service worker caches media but has no `push` event listener. `web-push` library is not present. The Cloudflare Worker only knows APNs. iOS Safari PWA users will get nothing.

**Fix:** Either ship Web Push (worker emits a VAPID-signed push → SW fires a notification), or document clearly that web/PWA gets only in-app toasts.

### H3 · Garden full-screen "growth / water" is hard-coded decoration — `apps/web/src/pages/GardenScreen.tsx:18, App.tsx:102`

`DEFAULT_STATS: GardenStats = { growth: 0.42, water: 0.72, health: 'thriving' }`. `App.tsx` calls `<GardenScreen onNavigate={...} />` with no `stats` prop. Every user sees the same 42% growth bar.

**Why it matters:** The Garden is the "research opt-in gift" per Decision #15. If the user opts into research and walks into a garden that's identical to their pre-opt-in mockup, the gift feels hollow. Worse: the brand book says Burhan never decays, but a static "water 72%" bar implies a water level — a Finch-trap pattern.

**Fix:** Either pipe real `burhan.events` length / recency into `growth` and remove the `water` metric entirely (it doesn't fit the "never decays" rule), or remove the bottom-bar UI and just show "burhan has grown N times this month" as a factual number.

### H4 · The reminder scheduler exists in two places — `apps/web/src/store.ts:115, apps/web/src/hooks/useApplyBrainDump.ts:24`

Both files call `createReminderScheduler(store, events)`. The first one calls `.init()` (rehydrates persisted reminders on boot). The second one doesn't — it's only used to call `.add(parsed)` when a brain dump produces a reminder. Each has its own `timers` Map closure. So new reminders are scheduled in the second instance's timers; persisted reminders are scheduled in the first instance's timers. They don't share state.

**Why it matters:** Cancelling a reminder from one instance won't cancel the timer in the other. Two instances also means two `void:reminder:fired` emits if there's ever a re-init.

**Fix:** Make `createReminderScheduler` return a module-level singleton, or pass the shared instance via a context. Pick the one in `store.ts` as canonical and import it in `useApplyBrainDump.ts`.

### H5 · UI components read `@ollie/logic/*` directly and re-run detectors in `useMemo` — `apps/web/src/modules/cycle/CycleModule.tsx:11-21, 561-582`

CycleModule imports and runs `predictNextPeriod`, `detectHealthFlags`, `fertileWindow`, `findCorrelations` inside `useMemo` on every relevant render. The doc in CLAUDE.md says "UI components never call logic directly — they read already-computed values from VOID.store." Same pattern in Grocery, Pets, Body, Work, Habits, Finance, Astrology.

**Why it matters:** Each detector also runs inside the corresponding orchestrator (which writes derived values to store on event changes). So the work happens twice. For cycle, that's a Bayesian posterior over every cycle every render. With 10+ cycles in memory and a typical re-render rate, that's a few ms of waste per interaction. More importantly: the architecture is drifting; the next contributor will either pile on more inline `useMemo` detectors or get confused about which value is authoritative.

**Fix:** Pick one. Either commit to "UI calls logic, orchestrator stops writing derived state" or commit to "UI reads `store.get('cycle', 'prediction')` and orchestrator owns the write." Both work; the current half-and-half is the worst.

### H6 · `body:doctor_visit_completed` registered but never emitted — `packages/events/src/registry.ts:176`

The event is on the burhan source list (creates a `canopy_fruit` element). Nothing emits it. So the most rewarding Burhan element type is unreachable.

**Fix:** When a doctor appointment is marked complete in admin (orchestrator/admin.ts:317 already emits `admin:appointment_completed` with `kind: 'doctor'`), burhan already accepts that event and picks the right element type from `kind` (orchestrator/burhan.ts:75). So just delete `body:doctor_visit_completed` from the source list and the registry.

### H7 · `void:toast` is emitted but not in the events registry — `packages/router/src/scheduler.ts:44`

Every reminder fire emits an unregistered event → console warn → noise. Same pattern likely elsewhere.

**Fix:** Add `'void:toast': { payload: '{ message: string, module: string }' }` to registry.ts. Then sweep for other unregistered emits.

### H8 · STATUS_CHECK_2026-05-11.md is stale and misleading

The status check says HEAD is "RED on main" because of `recentBurhanEvents`. Build + typecheck are clean. The status doc says "921 tests passing" — actual count is 1067 passing / 2 failing. The repo has ~67k lines, not 51k. Sprint summaries also overstate "shipped" (see C2).

**Why it matters:** Founders make sprint-planning decisions off these docs. If they're wrong, you ship the wrong thing.

**Fix:** Either delete the file or regenerate it as part of every sprint summary. Better: write a `pnpm status` script that emits these stats from real `git log`/`wc`/`pnpm test` output so it can't drift.

### H9 · Three.js is 945 KB un-gzipped (255 KB gz) — `apps/web/dist/assets/vendor-three-*.js`

That's a quarter of your initial download budget for the 3D Burhan. Burhan3D imports react-three-fiber + three. It's used in two places: the dashboard mini-tile (66×66 px!) and the full garden.

**Why it matters:** On 4G cell, this adds ~1-2s of cold-start. The Three.js feature is purely visual — the canopy renders just as well in canvas-2D (which BurhanTree.tsx already does for the home/cycle/grocery contexts).

**Fix:** Use canvas-2D BurhanTree everywhere except `/garden`. Lazy-load Burhan3D only when the garden route is hit. Probably trims 250 KB off cold start.

## 4. MEDIUM findings

### M1 · `store.set` mutates the cached state in place — `packages/store/src/store.ts:130-133`

`const state = readModule(mod) ?? {}; state[key] = value;`. The cache and any subscriber who held a reference both see the new value. Subscribers using shallow-equality (most React selectors) won't re-render because the parent reference didn't change.

**Why it matters:** Random "the dashboard doesn't update until I refresh" bugs. The bug surface grows as you add subscribers.

**Fix:** Clone before mutate — `const state = { ...readModule(mod) }; state[key] = value;`. Same in `remove`.

### M2 · Migration failure is logged not surfaced — `packages/store/src/migrations.ts:60`

`console.error` only. User sees nothing. Same pattern in many `catch { /* registry warn ok */ }` blocks throughout sync.ts, orchestrator files. Most are fine. Migration is special.

**Fix:** See C5. Migration failures must surface.

### M3 · `Burhan3D` is used at 66×66 px on dashboard — `apps/web/src/pages/DashboardScreen.tsx:262`

It's a WebGL canvas rendering an olive tree at thumbnail size. Burns a render context for a sprite that could be a static SVG.

**Fix:** Use the canvas-2D BurhanTree at small scale instead. Saves WebGL context + perf, especially on iPad-class hardware.

### M4 · Service worker doesn't precache the JS bundle — `apps/web/public/sw.js:14`

`PRECACHE` is just media. The first paint depends on `/index.html` and the chunked JS — which are not cached. So offline second-visit users get a cream-colored 404 page.

**Fix:** Add a stale-while-revalidate strategy for `/assets/*.js` and `/assets/*.css`.

### M5 · `_eventLineage` capped at 200 entries → silent loss past 200 — `packages/router/src/cross-module.ts:62, 254-259`

This is fine for debug, but the comment says "future debug surface" — there is no debug surface yet. So the 200-entry cap is invisible to the user but is the only memory the system has of "why did finance show me a cycle card?"

**Fix:** Build the debug surface (~½ day) — a hidden settings page showing the last 200 lineage rows.

### M6 · `void:toast` emit when reminder fires → no confirmed listener

The router fires `void:toast`. Trace one reminder fire end-to-end and confirm the toast renders. If not, wire it.

### M7 · `__lastCallTs` rate-limit in Anthropic client is per-module-singleton — `packages/api/src/anthropic.ts:17`

Two browser tabs share it via module reload, but in production they don't (each tab has its own JS). Not a security issue but means the rate-limit gate is weaker than the 3-second minGap implies.

### M8 · `passphraseStrength` is a "crude" length×classes scorer — `packages/crypto/src/index.ts:204-228`

It'll pass `aaaaaaaaaaaaaaaaA1` as "ok" (16 chars + 3 classes). The strength meter creates false confidence.

**Fix:** Cheap option: blacklist the most-common-1000 passwords.

### M9 · Two `createReminderScheduler` instances — see H4 for fix.

### M10 · `DEFAULT_MODULES` in sync hard-codes the list — `packages/sync/src/index.ts:73`

If you add a module ("medication" was added in Sprint 4), it won't sync. Today, `medication` is NOT in the list.

**Fix:** Add `medication` to the list, or derive dynamically from the store's known modules.

### M11 · `MIN_PASSPHRASE_LENGTH = 16` and `MIN_LENGTH = 16` declared separately — `packages/crypto/src/index.ts:202, 235`

Two constants both = 16. If one is bumped, the other won't follow.

**Fix:** Export one, use it everywhere.

### M12 · Aggregator dedupe key uses earliest enqueuedAt — fine in practice, document as such.
